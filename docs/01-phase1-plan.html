01このフェーズのゴール

完了条件は「ブラウザで 1 日分の食事を記録し、目標に対する達成状況が見える」こと。横に機能を広げるより、縦に 1 本通すことを優先する。動くものが手元にあれば、次に何が足りないかは自分で使えば分かるため。

やることやらないこと（後続フェーズ）
食品名の検索と手入力による記録バーコードスキャン（Phase 3）
カロリーと PFC の日別集計詳細栄養素・週別月別集計（Phase 3）
体重記録と推移グラフ運動記録・消費カロリー（Phase 4）
Mifflin-St Jeor による目標算出写真からの AI 推定（Phase 4）
テンプレート／履歴からのコピーKotlin 実装・Expo アプリ（Phase 2）
Phase 2 を見据えた進め方

ここで確定させる API 仕様は、そのまま Kotlin 実装が満たすべき契約になる。実装より先に api/openapi.yaml を書き、それに合わせて実装する順序を崩さないこと。順序が逆になると仕様が実装に引きずられ、Phase 2 で「Java 版の都合」が Kotlin 側に漏れる。

02API 設計

すべて /api 配下。/api/auth/* 以外は認証必須で、データは常にログイン中のユーザーでスコープする。

2.1食品マスタ

メソッド / パス内容
GET /api/foods食品名の部分一致検索。query と limit。自分が登録した食品も検索対象に含む。
POST /api/foodsマスタに無い食品をユーザーが登録する。source=USER として保存し、登録者本人だけが検索できる。

2.2プロフィールと目標

メソッド / パス内容
GET /api/profile身体情報。未設定なら 404。
PUT /api/profile性別・生年月日・身長・活動レベルの登録／更新（upsert）。
GET /api/goals/suggestionBMR・TDEE・目標カロリー・目標 PFC の提案を返す。保存はしない。
GET /api/goals/current今日時点で有効な目標。
PUT /api/goals目標を確定して保存する。

提案と保存を分けているのは、算出結果をそのまま押し付けず、ユーザーが数値を見てから調整できるようにするため。提案 API は副作用を持たない純粋な計算であり、テストも書きやすい。

2.3記録

メソッド / パス内容
GET /api/meal-logsdate 指定でその日の食事記録一覧。
POST /api/meal-logs食事を記録する。食品 ID と分量を渡すと、サーバー側で栄養値を計算してスナップショットを作る。
DELETE /api/meal-logs/{id}削除。他人の記録を指定した場合は 404。
GET /api/body-recordsfrom〜to の体重推移。
PUT /api/body-records/{date}その日の体重を登録／上書き（upsert）。

2.4集計

メソッド / パス内容
GET /api/summaries/daily指定日の摂取カロリー・PFC、目標との差分、食事区分ごとの内訳。ダッシュボードの主データ。
GET /api/summaries/rangefrom〜to の日別集計と体重推移。グラフ用。
他人のデータに到達させない

ID を指定して取得・削除する API は、すべて「ID が一致し、かつ user_id が自分である」条件で引く。存在しても他人のものなら 403 ではなく 404 を返す。403 だと「その ID は存在する」ことを教えてしまうため。この挙動は結合テストで検証する。

03目標カロリーの算出

採用式は Mifflin-St Jeor。体重はプロフィールではなく 体重記録の最新値を使う。体重は日々変わるものであり、プロフィールに固定値として持たせると実態とずれるため。

BMR（男性） = 10 × 体重kg + 6.25 × 身長cm − 5 × 年齢 + 5
BMR（女性） = 10 × 体重kg + 6.25 × 身長cm − 5 × 年齢 − 161

TDEE = BMR × 活動係数
  SEDENTARY   1.2     ほぼ座位
  LIGHT       1.375   軽い運動（週1〜3回）
  MODERATE    1.55    中程度（週3〜5回）
  ACTIVE      1.725   激しい（週6〜7回）
  VERY_ACTIVE 1.9     非常に激しい

目標摂取カロリー = TDEE − 1日あたりの目標赤字
  体脂肪 1kg ≒ 7,200 kcal
  1日の赤字 = 月間目標減量kg × 7200 ÷ 30

目標 PFC（既定値）
  P 20% / F 25% / C 55%
  g 換算  P,C は 4 kcal/g、F は 9 kcal/g

3.1安全側の下限を設ける

減量ペースを大きくすると目標カロリーが際限なく下がってしまう。算出結果が BMR を下回る場合は BMR を下限として打ち切る。あわせて、下限に張り付いたことを応答に含め、画面で「このペースは達成できない」と伝えられるようにする。

この機能は医療ではない

Mifflin-St Jeor は推定式であり、個人差がある。健康上の判断に使うものではないことを画面にも明記する。

3.2実装方針

算出ロジックは DB もリクエストも触らない純粋関数として切り出す。理由が 2 つある。ユニットテストが値の入出力だけで書けること、そしてPhase 2 で Kotlin に移植したときに、同じテストケースをそのまま流して等価性を確認できること。言語比較の題材としても、副作用のない計算は差分が読み取りやすい。

04食品マスタのデータ

本来の出典は日本食品標準成分表（文部科学省）だが、Phase 1 ではまず MVP を通すことを優先し、代表的な食品に絞ったシードデータを Flyway で投入する。

データの出所を偽らない

シードデータは source = 'SEED' として登録し、成分表由来の MEXT とは区別する。おおよその代表値であり、正確な栄養計算には使えない。Phase 3 で公式の成分表 CSV を取り込み、MEXT として置き換える。この区別を付けずに MEXT を名乗らせると、後から「どの値が検証済みか」が分からなくなる。

ユーザーが登録した食品は source = 'USER' となり、登録者本人の検索にのみ現れる。Phase 3 のバーコード機能で「マスタに無い商品を手動登録して自分のマスタを育てる」動線は、この仕組みをそのまま使う。

05栄養値スナップショットの生成

Phase 0 で用意した meal_log_items の非正規化を、ここで実際に使う。記録時の処理は次のとおり。

1

クライアントは食品 ID と分量だけを送る

栄養値をクライアントに計算させない。計算式がクライアントとサーバーに二重に存在すると、Web とモバイルで結果がずれる余地が生まれる。

2

サーバーがマスタを引いて 100g あたりから換算する

その食品の栄養値 = マスタの値(100gあたり) × 分量g ÷ 100
3

換算結果を meal_log_items の行に書き込む

食品名も一緒に複写する。マスタから食品が消えても、記録には何を食べたかが残る。

丸め方を先に決めておく。換算結果は小数第 2 位まで保持し、画面表示の段階で整数に丸める。DB 側で丸めると、1 日分を合計したときに誤差が積み上がるため。

画面内容
ログイン / 新規登録メールとパスワード。トークンは保持し、期限切れ時は自動でリフレッシュする。
ダッシュボード最上部に当日の 摂取 kcal / 目標 kcal / 残り。その下に PFC バランス、直近 30 日の摂取カロリーと体重の推移グラフ。

グラフは外部ライブラリを使わず、SVG を直接描く。CDN を参照しない方針であること、必要な表現が折れ線と面の塗りに限られること、そして Phase 2 で Expo 側に持っていく際に依存を増やしたくないことによる。

6.1体重の 7 日移動平均

体重は水分量で日々 1kg 前後動くため、実測値だけでは傾向が読めない。実測点は薄く、移動平均線を主役として描く。記録が無い日は平均の計算から除外し、線を途切れさせずに繋ぐ。

09実装で決めたこと

9.1栄養値をクライアントに計算させない

記録の API は食品 ID と分量だけを受け取る。栄養値をリクエストに含めない設計にしたため、クライアントが値を偽装して送っても無視される。計算式がクライアントとサーバーに二重に存在すると、Web とモバイルで結果がずれる余地が生まれるためで、この挙動は結合テストで検証している。

9.2合算時の任意項目の扱い

塩分・食物繊維・糖質はデータが無い食品がある。合算の際、片方が未設定なら 0 として加算する。合計自体を未設定にすると「1 品でも塩分不明なら 1 日の塩分が表示されない」ことになり、実用に耐えないため。両方とも未設定のときだけ未設定を保つ。この規則は Nutrition 1 箇所に閉じており、集計を SQL の sum() でなくアプリケーション側で行っているのも同じ理由による。

9.3他人のデータに到達させない

ID 指定の取得・削除は、クエリの条件に user_id を含めている。取得後に所有者を確認する方式だと、確認を書き忘れる余地が残るため。他人のリソースは403 ではなく 404 を返す。403 だと「その ID は存在する」ことを教えてしまう。他人が登録した独自食品も同様に、検索にも記録にも使えない。

9.4トークンの持ち方

アクセストークンとリフレッシュトークンは localStorage に置いている。HttpOnly Cookie の方が XSS には強いが、Phase 2 で同じ API を Expo から叩くため、ブラウザの Cookie に依存しない持ち方に揃えた。学習用途としての割り切りであり、商用なら再検討すべき点として記録しておく。

あわせて、リフレッシュ処理は同時多発しないよう 1 本の Promise に束ねている。ダッシュボードは複数の API を並列で呼ぶので、トークン失効時にリフレッシュが同時に走ると、ローテーションで互いを失効させてしまうため。

9.5グラフを 2 段に分けた

カロリーと体重は縦軸の単位が違う。1 つの図に 2 軸を詰めると目盛りの対応が読み取りにくいため、横軸だけを揃えた 2 段構成にした。外部のチャートライブラリは使わず SVG を直接描いている。
