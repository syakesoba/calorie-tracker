02起動方法

初回は 1 と 2 を実行する。2 回目以降は 3 だけでよい。

1

環境変数ファイルを用意する

既定値のままでも動くが、JWT の署名鍵を自分の値に変えたい場合はここで設定する。

cd C:\work\03_claude\02_Java
copy .env.example .env
2

データベースを起動する

初回起動時にのみ db/init/*.sql が実行され、ロールとテスト用データベースが作られる。

docker compose up -d db
3

バックエンドを起動する

起動時に Flyway が未適用のマイグレーションを流し、Hibernate がスキーマとエンティティの整合を検証する。

cd backend-java
.\gradlew.bat bootRun
4

起動を確認する

{"status":"UP"} が返れば成功。

curl http://localhost:8080/actuator/health

2.1テストの実行

テストは DB が起動している必要がある。開発用の calorie ではなくテスト専用の calorie_test を使うため、手元の開発データは壊れない。各テストはトランザクションでロールバックされる。

docker compose up -d db
cd backend-java
.\gradlew.bat test

2.2停止と作り直し

# 停止（データは残る）
docker compose down

# データごと破棄して初期化からやり直す
# ロールや初期化 SQL を変更したときは、これをしないと反映されない
docker compose down -v
docker compose up -d db
注意

db/init/*.sql はボリュームが空のときにしか実行されない。初期化 SQL を編集しても、既存のボリュームがあれば無視される。反映するには docker compose down -v が必要になる。

05設計判断の記録

5.1DB ポートを 55432 にした

この PC には PostgreSQL 16 と 18 が Windows サービスとして常駐しており、5432 を占有していた。当初 5432 でマッピングしたところ、Docker は IPv6 側にしか束縛できず、JDBC が IPv4 の localhost:5432 へ繋いだ結果、ネイティブの PostgreSQL に接続して認証エラーになった。

既存のローカル PostgreSQL には手を加えない方針としたため、Docker 側を 55432 に逃がした。

5.2Testcontainers を採用しなかった

当初はテスト実行のたびに使い捨ての PostgreSQL を立てる Testcontainers を採用する予定だった。しかし Docker Desktop 29.7.2 では docker-java が名前付きパイプ越しの info 応答を解釈できず、Docker を検出できなかった（Testcontainers 1.20.4 / 1.21.3 の双方で再現。DOCKER_HOST の明示指定でも解消せず）。

代替として、Docker Compose 上に calorie_test データベースを用意し、そこへ接続する方式にした。テストは @Transactional でロールバックされるため、テスト間の独立性は保たれている。H2 で代用しなかったのは、PostgreSQL 固有の CHECK 制約や型の挙動を本番と同じ条件で検証したいため。

Kotlin 実装への申し送り

Kotlin 側も同じテスト方式（calorie_test + @Transactional）にすること。片方だけ Testcontainers にすると、テストの書き味の差が「言語の差」なのか「テスト基盤の差」なのか分からなくなり、比較が成立しなくなる。

5.3スキーマの所有者を Java 側だけにした

1 つのスキーマに 2 つのアプリが接続する構成は、放置すると必ず壊れる。そこで権限レベルで事故を防いでいる。

  • app_java が public スキーマの所有者。Flyway はこの権限で DDL を実行する。
  • app_kotlin には SELECT / INSERT / UPDATE / DELETE のみ。実際に CREATE TABLE を試すと permission denied for schema public になることを確認済み。
  • 今後 app_java が作るテーブルにも自動で DML 権限が付くよう、ALTER DEFAULT PRIVILEGES を設定してある。テーブル追加のたびに GRANT を書く必要はない。
  • ユーザーを分けてあるため、pg_stat_activity やログでどちらのアプリが発行した SQL か追える。

5.4栄養値をスナップショットで持つ

meal_log_items は foods を参照するだけでなく、登録時点の栄養値を自分の行に複写して保持する。食品マスタは成分表の改訂やユーザーの修正で変わるが、「その日に何 kcal 食べたか」という記録が後から書き換わってはならないため。正規化のセオリーから外れた意図的な非正規化であり、整理のために削ってはならない。

5.5認証の設計

  • アクセストークンは自己完結型の JWT。DB を引かずに検証でき、有効期間は 30 分。
  • リフレッシュトークンはランダム文字列で、DB には SHA-256 ハッシュのみを保存する。DB が漏れてもトークン自体は復元できない。
  • ローテーション。更新に使ったリフレッシュトークンはその場で失効させ、新しいものを発行する。盗まれたトークンが再利用されたとき、正規の利用者が先に使っていれば弾ける。
  • ユーザー列挙対策。ユーザーが存在しない場合もダミーの BCrypt ハッシュと照合して処理時間を揃え、応答本文も完全に同一にしている。テストでこの同一性を検証している。
  • CSRF は無効。Cookie ではなく Authorization ヘッダで認証しており、ブラウザが自動で資格情報を送らないため。

07つまずいたときは

起動時に「password authentication failed for user "app_java"」が出る

Docker のコンテナではなく、PC に常駐しているネイティブの PostgreSQL に接続している可能性が高い。接続先が localhost:55432 になっているか確認する。

また、db/init/*.sql を編集した後にボリュームを作り直していない場合、ロール自体が存在しない。docker compose down -v の後に docker compose up -d db を実行する。

「Schema-validation: missing table」で起動に失敗する

Flyway のマイグレーションとエンティティの定義がずれている。ddl-auto=validate はこのずれを検知するために意図的に設定してあるので、設定を緩めるのではなくマイグレーションかエンティティを直す。絶対に update に変えないこと。

テストが「Unable to obtain connection from database」で失敗する

DB が起動していない。テストは Testcontainers を使わないため、事前に docker compose up -d db が必要。

ポート 8080 が既に使われている

前回の bootRun が残っている可能性がある。次のコマンドで確認して停止する。

Get-NetTCPConnection -LocalPort 8080 -State Listen
DB の中身を直接見たい 
docker exec -it calorie-db psql -U postgres -d calorie

テーブル一覧は \dt、テーブル定義は \d users で確認できる。
